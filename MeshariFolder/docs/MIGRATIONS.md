# Database migrations (Alembic)

Until now the schema was built by `Base.metadata.create_all()` on every
startup. `create_all` creates **missing tables** but never adds a **missing
column** to a table that already exists. The schema changed shape many
times, and one of those changes (a new `onboarding_stage` column with no
migration to backfill it) stranded real accounts on the onboarding screen.
Migrations replace that: every schema change is now a small, reviewed,
versioned file, and the app applies whatever the database is missing when
it starts.

## What happens at startup

`app/migrations.py → upgrade_database()` looks at the database and does one
of three things:

| The database is… | It… |
|---|---|
| **empty** (first run, or a deleted `dev.db`) | builds everything by running every migration from the start |
| **already under Alembic** | runs only the migrations newer than its version |
| **a "legacy" DB** — built by the old `create_all`, has tables but no `alembic_version` | checks it against the frozen baseline (`0001`); if it matches, *adopts* it (stamps `0001`, then upgrades). Nothing is lost. |

If a legacy DB does **not** match — the classic out-of-date dev database —
the app refuses to start and says exactly what's missing, e.g.
`column 'users.onboarding_stage' is missing`. That is on purpose: a loud
error at startup beats a mystery 500 in the middle of a request. The fix is
in the message: delete the SQLite file (it's disposable) or, for a shared
Postgres you want to keep, add the missing columns by hand and restart.

When two API processes start at the same moment on Postgres, they take
turns via an advisory lock (tested with four at once).

## Everyday workflow: changing the schema

1. Edit the model in `app/models.py`.
2. Generate the migration (from `backend/`, venv active):

   ```powershell
   alembic revision --autogenerate -m "add preferred_language to users" --rev-id 0003
   ```

3. **Open the generated file in `alembic/versions/` and read it.**
   Autogenerate is a draft, not an oracle (see gotchas).
4. Run the app or `python smoke_test_migrations.py` — it applies the new
   migration to a fresh database and to an adopted legacy one.
5. Commit the model change and the migration **together**.

Other handy commands: `alembic current`, `alembic history`,
`alembic upgrade head`, `alembic downgrade -1`,
`alembic upgrade head --sql` (print the SQL instead of running it).

## The drift guard

`smoke_test_migrations.py` compares the migrations against the models. If
someone edits a model and forgets the migration, that check fails with the
exact command to run. This is the check that keeps the original bug from
coming back — it is the reason the suite exists, more than any single
migration.

## Gotchas (learned while building this)

- **Adding a NOT NULL column to a table that already has rows** needs a
  `server_default` (or a backfill step) in the migration, otherwise it
  fails on any database with data in it. Autogenerate won't warn you.
- **Postgres enums are separate database objects.** Dropping a table does
  not drop its enum types (the baseline's `downgrade()` does this by hand —
  found on real Postgres, invisible on SQLite). Adding a value to an
  existing Python enum needs `ALTER TYPE <name> ADD VALUE '<VALUE>'` in the
  migration; autogenerate doesn't produce it. Enum values are stored by
  member **name** (`JUNIOR_DEV`), not by the lowercase string value.
- **SQLite can't ALTER most things**, so `env.py` turns on
  `render_as_batch`: autogenerated migrations use `batch_alter_table`,
  which rebuilds the table on SQLite and issues plain `ALTER` on Postgres.
- **A column rename looks like a drop + add** to autogenerate — which would
  delete the data. Write `op.alter_column(..., new_column_name=...)` by
  hand.
- **Never edit a migration that's already been merged.** Add a new one.
- **Two branches, one number.** Migrations are numbered `0001`, `0002`, …
  If two open PRs both create `0003`, the second to merge must be renamed
  to the next free number and its `down_revision` pointed at the first
  (`alembic heads` shows if you've ended up with two).

## What was verified

- SQLite and **PostgreSQL 16**: fresh build, re-run (no-op), legacy
  adoption with data intact, stale legacy refusal, full downgrade to base
  and back up again, models-vs-migrations drift check.
- Every existing smoke suite (all 15) passes on both databases now that
  they start through migrations.
- Four simultaneous startups on an empty Postgres: exactly one builds the
  schema, the rest wait and no-op, zero errors.

To repeat the Postgres checks yourself (this drops the `public` schema of
the database you point it at, so use a disposable one):

```powershell
docker compose up -d
$env:MIGRATIONS_TEST_POSTGRES_URL = "postgresql://venv:venv@localhost:5432/venv_test"
python smoke_test_migrations.py
```

## Not covered

- **Data migrations at scale.** These are schema migrations for a small
  app; backfilling millions of rows would want batching.
- **Zero-downtime deploys.** Migrations run at startup, before the app
  serves traffic. Fine for this project; a bigger deployment would run
  `alembic upgrade head` as a separate release step.
